# Design

## Context

动机与范围见 [proposal.md](proposal.md)。本变更建立在 `add-parallel-segment-download` 之上（截至 `7172646`），复用其连接数配置、共享地址租约和分段协调器。

### 现状

- `Engine.step(signal)`（`src/runtime/engine.ts`）一次完成一个工作单元：要么扫描一个分享，要么把一个文件从“检查副本 → 空间计划 → 转存 → 下载 → 校验 → 发布”整条流水线做完才返回。扫描和文件交替进行（`preferFile`）。
- `RuntimeSession`（`src/runtime/session.ts`）循环调用 `step`，每一步一个中断控制器；命令在两次步骤之间执行。取消当前文件或暂停队列时，先中断当前步骤并等待它返回，再写任务库。会话只跟踪一个当前执行项。
- 进度事件节流是全局的：`Engine` 只有一个 `lastProgress`，每 250 ms 最多发一次。
- 空间计划 `SpaceManager.ensure(needed)` 以服务端容量的剩余量为准。已转存但尚未交付的副本已经计入已用容量；回收候选只包含已交付且有归属证据的副本，因此正在下载的副本永远不会被回收。
- 2026-10-15 的 P1 实测表明 CDN 按单个连接限速（每个连接约 31–65 KiB/s），8 个连接合计没有触发限流；`add-parallel-segment-download` 让单个大文件最多用 8 个连接。

### 由此得出的约束

- 大文件已经能用满 8 个连接。在全局 8 连接预算下，多文件并发的收益主要来自两处：许多小于 8 MiB 的小文件（每个只用 1 个连接）可以同时下载；每个文件固有的串行耗时（等待转存任务完成、整文件读回校验、发布）可以与其他文件的下载重叠。
- 转存保持串行，并且在转存前先占用一个“在途名额”，云端同时存在的未交付副本就不超过 N 份。这时服务端容量本身就反映了在途副本，现有空间计划不需要另一套预留账本。

## Goals / Non-Goals

**Goals:**

- 设置“同时下载的文件数” N（1–5，默认 1）；N = 1 时行为与现在完全一致。
- 免费账号上限 1，会员最多 5；等级读取方式和两个上限先经真实账号验证（P3）。
- 扫描与转存串行，下载阶段最多 N 个文件同时进行；所有在途文件的 CDN 连接合计不超过 8。
- 取消、暂停、账号级暂停与中断对每个在途文件都在安全点停止，并保留可恢复状态。
- 全屏界面同时显示多个文件的进度，并在设置页修改 N。

**Non-Goals:**

- 并发扫描、并发转存、跨账号并发。
- 超过 8 个的总连接数；按文件大小自动调整并发数。
- 持久化的容量预留表（见决策 3）。
- 运行中重新分配已经开始的连接（只限制新连接，见决策 4）。

## Decisions

### 1. 先验证账号等级与多文件并发，再实现（P3）

| 编号 | 必须取得的证据 | 通过标准 | 未通过时 |
| --- | --- | --- | --- |
| P3a 账号等级 | 用本工具已授权的权限，找到能稳定区分免费与会员的只读接口：优先 `/drive/v1/privilege/vip` 一类会员接口；不可用时评估 `/drive/v1/about` 的容量上限（免费 6 GiB、会员 10 TiB）能否作为判断依据。记录字段、取值和失败时的表现；不输出账号资料 | 有一个只读、无需额外授权的判断方式，失败时可以明确识别为“未知” | 等级一律按免费处理（上限 1），设置页说明原因；本变更其余部分照常实施但实际不放开并发 |
| P3b 多文件并发 | 用会员测试账号，在 2、3、5 个不同云端副本上同时下载（每个文件 1 个连接，合计不超过 8），各运行 3 次；记录合计吞吐、每个连接的速率、429/403/402 次数，以及服务端是否拒绝同时下载多个文件 | 合计吞吐随文件数近似线性增长，正常运行中没有 429/403 | 有限流时在 1–5 内调低会员上限后再评审；完全不允许时停止本变更 |

免费账号的上限 1 来自用户经验；本项目没有免费测试账号，因此不单独验证，按 1 处理。P3 的结果记录到本文件的 Evidence 小节，验证程序沿用 `spikes/segment-download/` 的做法：持有执行锁、只读取本工具任务库中保留的副本、不写本地文件、不输出签名地址、凭据或文件名。

### 2. 执行模型：串行准备 + 有界下载池

把文件流水线拆成两段：

```
step()（串行，同一时刻一个）            下载池（最多 N 个）
┌──────────────────────────────┐       ┌───────────────────────────────┐
│ 扫描分享                      │       │ 文件 A：下载 → 校验 → 发布     │
│ 或：选下一个文件               │       │ 文件 B：下载 → 校验 → 发布     │
│   占用在途名额（没有空位不选）  │──────▶│ …                              │
│   检查副本 / 空间计划 / 转存    │ 交给池 │ 完成或失败后释放名额           │
└──────────────────────────────┘       └───────────────────────────────┘
```

- `step()` 只做串行工作：扫描，或为下一个文件占用名额、检查已有副本、做空间计划并转存。转存完成后把“下载 → 校验 → 发布”交给下载池，立即返回。没有空位时不选新文件，但仍可以扫描。
- 下载池中的每个文件有自己的中断控制器，派生自会话的运行信号而不是单步信号，因为它比创建它的那一步活得久。池中任务的错误按现有 `step` 的分类处理（本地空间、目标不可用、认证、流量、限流、版本变化、文件级失败），这段分类逻辑提取成 `Engine` 的一个方法，两处共用。
- 发布中的文件（`publishing` 或已有完整摘要的 `reconciling`）不需要转存，直接作为池任务进入，同样占用名额。
- `nextFile` 增加排除集合，跳过已在池中的文件；同一文件版本仍然只有一个活动执行项（对应“并发请求与扫描结果合并”）。
- **N = 1 时**，`step()` 等待池中唯一的任务完成后才返回，扫描与文件的交替顺序与现在相同。这是“默认值 1 时行为不变”的保证，现有测试全部在这个模式下运行。

备选方案：

- 在 `RuntimeSession` 里同时运行 N 个 `step()`。被否决：`step` 内部的扫描、空间计划和转存都假定独占，需要在多处加锁，取消和暂停语义也难以说清。
- 把空间计划和转存也放进池，用持久化预留表协调。被否决：§3 要求的“显式容量预留”只是为了防止多个转存争抢容量；转存串行之后，“先占名额再转存”就足以把在途副本限制在 N 份，额外的预留表只会多出一份需要与服务端核对的状态。

### 3. 云端容量：名额即预留

- 名额在转存之前占用，在文件完成、失败、取消或中断时释放。同时存在的未交付副本最多 N 份。
- 空间计划不变：转存前用服务端容量判断 `free >= size`。已在池中的副本已经计入已用容量，不需要额外扣减。
- 回收资格不变：只有已交付且有归属证据的副本可以回收，池中文件的副本没有交付记录，不会成为候选。池中某个文件完成后，它的副本才可能在之后的空间计划中被回收。
- 等待空间：下一个文件放不下时按现有规则进入 `waiting_space`，并释放刚占用的名额；其他在途文件不受影响。池中有文件完成后，下一次 `step()` 会重新评估。

### 4. 全局连接预算

- 新建 `ConnectionBudget`（总量 8，所有在途文件共享），在下载池里登记在途文件。每个文件的份额为 `max(1, ⌊8 / 在途文件数⌋)`。
- 分段协调器的 `ConnectionGate` 在判断能否新建连接时，额外取 `min(当前并发, 预算份额)`。在途文件数增加、份额变小时，已经建立的连接继续传输，降到份额以下之前不补新连接，与限流降并发的规则相同。因此总连接数可能短暂超过 8，最多持续到超额连接完成手头的分块（不超过 8 MiB）。
- 小于等于一个分块的文件本来只用 1 个连接，不受份额影响，但仍占用 1 个预算。
- 备选：在途文件数变化时立即中断超额连接。被否决：中断会浪费已经在途的字节，而短暂超额对 CDN 的影响很小；P1 中 8 个连接没有触发限流。
- 余数不分配（例如 3 个文件各 2 个，合计 6），以保持规则简单；这对小文件为主的场景没有影响。

### 5. 设置与账号等级

- 新配置键 `max_active_files`，取值 1–5，默认 1；校验方式与 `download_connections` 相同（只接受整数字符串，非法值拒绝并保留原值）。
- 实际上限 `effective = min(max_active_files, tierCap)`，其中免费或未知等级 `tierCap = 1`，会员 `tierCap = 5`（P3 可以在 1–5 内调低）。等级在会话启动时读取一次，之后每 10 分钟刷新；读取失败时沿用上一次结果，从未成功时按未知处理。
- 设置页显示配置值与实际生效值；受等级限制时说明“免费账号同时只能下载 1 个文件”或“暂时无法读取账号等级”。`config --files <1-5>` 写入同一个键，`status` 同时显示配置值和账号等级。
- 新值在名额空出时生效：调低时不打断已在池中的文件，只是不再补充；调高时下一次 `step()` 就可以多选文件。

### 6. 会话、命令与暂停

- `RuntimeSession` 跟踪“串行步骤的当前项”和“池中文件集合”两类执行项，分别对应各自的中断控制器。
- 暂停队列：中断串行步骤和全部池中文件，等它们在安全点返回并保存检查点后写入 `queue_paused`。
- 取消文件：只中断目标文件（无论它在串行步骤中还是在池中），等它返回后写入取消标记；取消分享：中断该分享在途的所有文件。其他文件继续。
- 账号级暂停（认证、权限、本地空间、目标不可用、流量、数据库、限流）：任何一个池任务或串行步骤触发后，其余池中文件也在安全点停止。这些原因对整个账号生效，继续下载只会重复得到同样的错误。
- 中断（Ctrl+C、`q`）：中断全部执行项，并行等待它们保存检查点；全屏界面现有的 10 秒有界停止仍然适用。
- 进度节流改为按文件分别计算（每个文件每 250 ms 最多一次），避免一个文件的进度挤掉另一个文件的进度。

### 7. 界面

- 主面板已按文件保存进度，可以同时显示多行下载进度和动态图标，不需要改动列表结构。
- 标题栏在有下载时增加“下载中 n/N”和合计速度（各在途文件速度之和）；窗口窄时按现有规则先省略本地剩余与云盘，再省略合计速度。
- 设置页新增“同时下载的文件数”，←→ 在 1–5 之间调整，受等级限制时显示说明，并标出实际生效值。

## Risks / Trade-offs

- [服务端不允许同一账号同时下载多个文件，或按账号限制总并发] → P3b 先验证；不允许时停止本变更，默认值 1 不受影响。
- [等级判断依据不可靠，误把免费账号当会员] → 只在 P3a 找到明确依据后放开；未知时按免费处理；服务端拒绝时仍由现有限流与错误分类兜底。
- [多个文件同时写同一块磁盘，读回校验与写入叠加] → P2 中桥接合计读写约 26 MiB/s（SSD）和 13–17 MiB/s（机械硬盘），8 个连接的下载速率远低于此；Windows 文件桥本来就串行处理调用。
- [短暂超过 8 个连接] → 超额只持续到在途分块完成（不超过 8 MiB），之后不补连接。
- [某个文件的账号级错误打断其他文件] → 这类错误本来就对整个账号生效；被打断的文件保存检查点，恢复后从断点继续。
- [并发让调度顺序变得不确定，测试变脆] → N = 1 保持现有的确定性路径；并发路径用可控的假服务与条件等待测试，不依赖固定时长。
- [运行时会话复杂度上升] → 串行步骤与下载池分开跟踪，命令只与“目标执行项集合”交互；取消与暂停的语义逐项写入规格场景。

## Migration Plan

1. 先完成 P3a、P3b 并记录证据；P3b 不通过就停止本变更。
2. 新增配置键 `max_active_files`，不改变任务库结构版本（配置表本来就是键值）。未设置时为 1，现有行为不变。
3. 回退：设为 1 即恢复串行；回退到旧程序时它会忽略未知配置键。

## Open Questions

- P3a：哪个只读接口能可靠区分免费与会员；`about` 的容量上限能否作为后备依据。
- P3b：会员账号同时下载多个文件时是否另有限制；会员上限是否需要低于 5。
- 等级刷新间隔（暂定 10 分钟）是否需要更短，例如会员到期后立即降级。
