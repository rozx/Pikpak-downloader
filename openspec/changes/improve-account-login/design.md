## Context

授权请求的 `scope` 是 `openid profile`，PikPak 授权页另外让用户逐项勾选应用权限。2026-10-15 的实测授权范围是 `files:manage cloud_download share account`（见 add-task-controls 设计）。现有登录只核对身份与容量可读，不看授权范围。

全屏界面的运行时在 `tui/run.tsx` 中启动一次，会话结束即退出程序；`StartupApp` 进入主面板后不再回到登录阶段。

## Goals / Non-Goals

**Goals:**
- 在界面中查看账号、会员、容量与授权范围。
- 在界面中登出或重新授权，不必退出程序。
- 授权返回后立即发现漏勾的权限，并引导用户重新授权。

**Non-Goals:**
- 不改变授权请求的 `scope` 参数：服务端发现文档只列出 `openid profile email`，请求其他值可能被拒绝。
- 不用有副作用的操作探测权限，例如为了验证删除权限而创建再删除文件。
- 不改变运行中被拒绝时的暂停规则。

## Decisions

### 1. 权限定义

`auth/permissions.ts` 列出已知权限：

| scope | 名称 | 用途 | 必需 |
| --- | --- | --- | --- |
| `account` | 账号信息 | 读取身份、会员与容量 | 是 |
| `files:manage` | 管理文件 | 转存、下载与释放云端副本 | 是 |
| `share` | 分享 | 读取与转存分享 | 是 |
| `cloud_download` | 云下载 | 本工具暂不使用 | 否 |

`openid`、`profile`、`email`、`offline_access` 属于登录基础，不单独显示；其他未知值原样列出。用户要求“完全的权限”，但 `cloud_download` 不被使用，所以把它列为建议勾选，不强制。漏勾它不会触发重新授权。

### 2. 权限的判定：实际探测为主

服务端返回的授权范围不反映授权页的勾选结果（见 Evidence），发现文档也没有令牌内省端点（只有 `revocation_endpoint` 与 `jwks_uri`）。可靠的依据只剩服务端处理请求时的放行或拒绝，所以每项权限都用本工具实际会调用的接口探测（`pikpak/permission-probe.ts`）：

| 权限 | 探测 |
| --- | --- |
| `account` | `GET /drive/v1/privilege/vip` |
| `files:manage` | `GET` 与 `PATCH /drive/v1/files/<不存在的 ID>`（请求体 `{}`） |
| `share` | `GET /drive/v1/share?share_id=<不存在的 ID>` |
| `cloud_download` | `GET /drive/v1/tasks/<不存在的 ID>` |

探测没有副作用：要么是只读请求，要么是针对不存在 ID 的写请求。`PATCH` 的请求体为空，即使 ID 碰巧存在也不会改动任何内容。

判定规则：403 或权限类错误（`permission_denied`、`insufficient_scope` 等）为缺少；其他 4xx（不存在、参数无效）说明请求已通过权限检查，记为已授予；401、429、5xx 与网络错误无法判断。同一权限有多项探测时，任一缺少即缺少，全部通过才算已授予。探测直接带令牌请求，不经过 `PikpakClient`，所以被拒绝时不会暂停账号。

探测无法判断时，才参考授权范围。授权范围的来源是合并两处：令牌响应的 `scope`（RFC 6749 §5.1，空格分隔，也接受字符串数组），以及访问令牌为 JWT 时载荷中的 `scope` 或 `scp`。两处都没有时为“未知”。合并结果不含任何已知应用权限时，也按“未知”处理（见 Evidence）。

载荷只在进程内解码，不校验签名。这里只用来提示用户，不作为安全判断依据。令牌本身不输出。

授权范围保存在会话记录的可选字段 `scopes` 中。刷新响应带有 `scope` 时更新，否则沿用上一代。旧记录没有这个字段，读作未知。

### 3. 登录回调的核对

换取令牌后、保存之前，先用新令牌探测各项权限：

- 已知且缺少必需权限：不保存这次授权（旧会话保持不变），回调页列出缺少的权限，提供“重新授权”按钮，终端提示同样内容，登录继续等待，直到成功、取消或超时。
- 已知且齐全，或未知：沿用现有身份与容量核对后保存。

本地入口 `/authorize/<nonce>` 在上一次尝试已用掉或过期时生成新的 state 与 PKCE verifier，所以“重新授权”按钮可以重复使用。尝试尚未用掉时沿用原值，以免多开的标签页互相作废。

`login` 的非强制路径中，已有会话探测到缺少必需权限时，不复用它，改走浏览器授权。

账号页在打开时重新探测。CLI `permissions` 命令逐项打印探测结果（HTTP 状态与错误类别，不含令牌或地址），用于实机核对判定规则。

### 4. 本地页面

`auth/login-page.ts` 生成全部本地页面：入口、成功、权限不足和失败。页面使用内联样式，CSP 保持 `default-src 'none'; style-src 'unsafe-inline'`，不加载脚本、字体或外部资源，跟随系统深浅色。入口页分三步说明流程，并列出必须勾选与建议勾选的权限。动态文字一律做 HTML 转义。

### 5. 账号资料

`protocol.ts` 新增 `profile`，读取 `user/me` 的 `sub`、`name` 与 `email`（缺失时为空）。会员状态复用 `/drive/v1/privilege/vip`：`AccountTier` 除等级外保存会员类型与到期时间，供账号页显示。容量沿用快照中的 `quota`。

`LiveController` 的 `account` 选项按需读取资料，在启动时以及每次打开账号页时刷新；读取失败时保留上次结果。

### 6. 界面中的登出与重新授权

设置页第一项改为“账号”，显示摘要，按 Enter 进入账号页。账号页按 `r` 重新授权，按 `l` 登出，登出需要确认。

执行这两项操作时，`StartupApp` 先调用 `deps.suspend()`：中止运行时信号，在安全点停止会话，并释放实时控制器。会话结束不会因此退出程序。最多等待 30 秒；仍未停止时显示失败页并要求退出程序，不在同一任务库上启动第二个执行器。之后：

- 登出：暂停账号的“认证”，清除令牌，回到登录页。
- 重新授权：进入登录页并立即开始浏览器授权。登录页记住原账号，取消或失败时按 Esc 回到原账号的主面板。

启动时若探测到缺少必需权限，进入登录页并说明缺少哪些权限。用户可以按 Enter 重新授权，也可以按 Esc 暂时继续使用。

## Risks / Trade-offs

- [探测的分类依赖服务端对缺少权限返回 403] → 用 `permissions` 命令实机核对：全部勾选时应全部通过；漏勾某项时应显示缺少（tasks 5.2）。服务端行为不同时按实测调整判定规则。
- [探测只能证明请求通过了权限检查，不能证明业务一定成功] → 具体操作被拒绝时，仍按现有规则暂停并提示重新授权。
- [权限名称与授权页文字不完全对应] → 页面同时显示中文说明与 scope 原名，并提示“全部勾选”。
- [停止执行需要时间] → 最多等待 30 秒；超时后不继续登出或授权，提示退出程序，避免新旧执行器同时运行。
- [重新授权登录到另一个账号] → 沿用账号隔离规则：新账号成为活动账号，旧账号任务保留但不执行。

## Evidence

2026-10-15 实机登录（v0.6.0）：用户在授权页勾选了全部权限，登录回调仍判定账号信息、管理文件、分享三项全部缺少，并持续要求重新授权。由此可知，那几次令牌响应的授权范围存在，但不含任何应用权限。同一会话的转存、下载与删除都正常，说明实际权限是齐全的。

修正（v0.6.1）：合并令牌响应与 JWT 载荷中的范围；合并结果一项应用权限都没有时按“未知”处理，不阻止登录，账号页显示“无法确认”。会话中已保存的旧范围按同样规则解读。只有服务端确实返回了部分应用权限、缺少必需项时，才要求重新授权。

修正之二（v0.7.0）：v0.6.1 的做法只是不再误拦，仍然不知道实际权限。改为按决策 2 实际探测每项权限，授权范围只作为探测无法判断时的参考。

2026-10-15 实机核对（v0.7.0，`permissions` 命令，全部勾选后重新登录）：

| 探测 | 响应 | 判定 |
| --- | --- | --- |
| 读取会员 | 200 | 已授予 |
| 读取文件（不存在的 ID） | 404 `file_not_found` | 已授予 |
| 修改文件（不存在的 ID，空请求体） | 400 | 已授予 |
| 读取分享（不存在的 ID） | 200 | 已授予 |
| 读取云下载（不存在的 ID） | 404 | 已授予 |

这次会话保存的授权范围正是 `files:manage cloud_download share account`。可见服务端返回的授权范围时有时无：同样全部勾选，v0.6.0 的几次回调不含应用权限，这一次又完整。原因尚不清楚，因此不能依赖授权范围，以探测为准。漏勾时服务端是否返回 403，仍待负向核对（tasks 6.4）。
