# Design

## Context

动机见 [proposal.md](proposal.md)，可观察行为见 [share-downloads 规格增量](specs/share-downloads/spec.md)。本文以 `add-clipboard-download-workflow` 已实现的代码为基线：`src/download/`、`src/platform/` 的行号对应提交 `63597e8`，这些文件截至 `3111468` 未改动；`src/runtime/engine.ts` 已随 `add-interactive-tui` 改动，行号对应 `3111468`。

### 实测数据

2026-10-14 在 Windows 上实测：单个下载连接约 245 KiB/s；本地 Windows 文件桥写入约 21 MiB/s；每 8 MiB 一次的元数据请求开销很小。所以瓶颈在 CDN 单连接速度，而不在本地写入或 API 往返。本地写入大约有 80 倍余量，并发连接带来的额外写入和读回不会先撞上本地上限。“CDN 按单个连接限速、而不是按账号或 IP 总量限速”目前只是推断，必须由 P1 证实（见决策 1）。

### 现有机制与多连接下的改法

| 机制 | 现状（代码位置） | 多连接下的问题 | 本设计的改法 |
| --- | --- | --- | --- |
| 只有一个在途下载连接 | [transfer.ts:68-117](../../../src/download/transfer.ts) 的 `while (offset < file.size)` 每轮先 `check()` 重新取元数据和地址，再请求 `bytes=offset-(offset+8 MiB-1)`，读完一段才请求下一段；[engine.ts:181](../../../src/runtime/engine.ts) 每次只调度一个文件；原设计 §3 规定同一时刻最多一个转存/下载流水项，§6 规定“首版使用单连接顺序下载” | 每段都调用 `check()`，元数据请求数会随连接数成倍增加；`addressRetries`、`rangeRestarts` 都是单连接局部变量，多个连接会各自刷新地址、各自计数；429 会直接抛出并消耗文件级重试预算 | 仍然一次只下载一个文件（§3 不变），文件内部由调度器在有界窗口里分配 8 MiB 分块（决策 3）；地址与版本核对改为共享租约，最长 30 秒刷新一次，遇到 401/403 时单飞刷新（决策 6）；限流先在文件内部降并发（决策 7） |
| 断点检查点：顺序前缀 SHA-256 | `deliveries.checkpoint` 加 `prefix_sha256`，表示 `[0, checkpoint)` 的 SHA-256；[transfer.ts:54-56](../../../src/download/transfer.ts) 每新增 1 MiB 就先 `sync()` 再写库；恢复时 [transfer.ts:58-65](../../../src/download/transfer.ts) 用 `prefix()` 读回并比对，然后截断到检查点；`remainingBytes()` 在 [transfer.ts:31](../../../src/download/transfer.ts) 也会截断检查点之后的数据 | 并发写入时，已写数据不再是一个连续前缀，只用一个偏移量无法描述；截断会删掉窗口内已经完成的分块；SHA-256 不能拼接，无法由“前缀摘要 + 分块摘要”直接算出新前缀摘要 | 保留连续前缀的原有含义，另加最多 16 个分块区间，每个区间各自记录 SHA-256（决策 4）；前缀之后紧接的分块完成后，先读回再并入前缀（决策 5）；恢复时分别核对前缀和每个区间，只丢弃对不上的区间，并且不再截断前缀之后的数据（决策 4、9） |
| 流式 GCID 校验 | [transfer.ts:111](../../../src/download/transfer.ts) 收到的网络字节按顺序送入 `ContentHasher`（[gcid.ts](../../../src/download/gcid.ts)，同时计算 GCID 与 SHA-256）；下载结束后先比对 GCID，再通过 `hashFile` 读回，比对 GCID 与 SHA-256（[transfer.ts:119-123](../../../src/download/transfer.ts)） | GCID 是“各块 SHA-1 依次拼接后再做 SHA-1”，SHA-256 是整条流的摘要，两者都要求按顺序输入；乱序到达的分块不能直接送进同一个哈希器 | 每个连接只对自己负责的分块计算 SHA-256；顺序哈希器只吃“已经读回、并与该分块接收时摘要一致”的磁盘数据，前缀推到文件末尾时得到 GCID 与 SHA-256；完成后的读回校验和发布流程不变（决策 5） |

### 与原设计其他决策的关系

- §3 单执行器：保持不变。分段只发生在一个文件内部，云端始终只有这一份副本，因此不需要 §3 所说的“跨文件容量预留”。
- §6 校验与交付：“首版使用单连接顺序下载”由本设计替换为“支持 Range 时有界并发，否则单连接顺序下载”。§6 的其余约束改为对每个分块请求分别成立：核对 Range 状态、起始位置、总长度和内容版本；出现 200 或范围不匹配时不追加；不把错误页、其他版本或压缩后的字节当作原文件。
- §7 空间计划：保持不变。云端需求仍按单个文件计算；下载期间该副本有活动使用者，不会成为回收候选。只有本地容量预检的计算方式受影响（决策 9）。

### 平台约束

- Windows 文件桥：[process-bridge.ts:20-21](../../../src/platform/process-bridge.ts) 把所有请求放进同一个 FIFO 队列，一次只有一个调用在途，每个调用最多 15 秒（第 27 行）。[windows-files.ts:21-24](../../../src/platform/windows-files.ts) 每次写 64 KiB，并在调用中给出偏移量；C# 端每次调用都先设置 `Stream.Position` 再写入。因此多个连接即使并发调用，也不会争用文件位置，只会排队。
- NTFS 有“有效数据长度”（VDL）：在 VDL 之后写入，会先把中间空缺补零。这一行为来自平台常识，尚未在本项目实测，由 P2 验证。
- macOS：[mac-files.ts:29](../../../src/platform/mac-files.ts) 用带位置参数的 `write`，对同一 fd 的不相交区间并发写入是安全的；APFS 支持稀疏文件，不会补零。

## Goals / Non-Goals

**Goals:**

- 在 CDN 按单连接限速的前提下，把单个大文件的下载速度提高到接近“连接数 × 单连接速度”。默认 4 个连接，预计约 1 MiB/s，10 GiB 约 3 小时。
- 在多连接下保持现有保证：只续传能够核对的数据；每个响应必须精确覆盖请求范围；最终交付仍经过 GCID 与读回校验；版本一旦变化就不拼接。
- 旧检查点无需重下即可继续使用；配置为 1 个连接时，行为与现在一致。
- 遇到 429/403 时先降低自身压力，不把连接级波动直接变成文件级失败。

**Non-Goals:**

- 多个文件同时下载、跨文件容量预留、调整单执行器模型。
- 修改 Windows/macOS 原生文件桥接（预分配、稀疏文件、多句柄）。
- 动态分块大小、拆分队头分块、CDN 节点选择。
- 改变进度事件结构或 TUI 展示（由 `add-interactive-tui` 负责）。

## Decisions

### 1. 先验证真实 CDN 与 Windows 文件桥，再实现

沿用原变更“先验证关键链路”的做法。验证只使用明确指定的测试副本（大于等于 256 MiB），不把签名地址、凭据或文件名写进仓库或输出。

| 编号 | 必须取得的证据 | 通过标准 | 未通过时 |
| --- | --- | --- | --- |
| P1 真实 CDN | 同一个签名地址上，用 1/2/4/8 个并发 Range 连接各运行 3 次，记录合计吞吐、每个响应的状态码与 `Content-Range`，以及 429/403/402 的次数和 `Retry-After`；确认多个连接可以共用同一个签名地址；测量地址从取得到 401/403 失效的时长 | 4 个连接的合计吞吐不低于单连接的 2.5 倍，正常运行中没有 429/403 | 4 个连接不到 1.3 倍时停止本变更，记录证据，保持单连接；有增益但频繁 429/403 时，在 1–8 内调低默认值后再评审 |
| P2 Windows 文件桥 | 用编译后的产物在 NTFS 上运行：4 和 8 个写入者，在 64 MiB 和 128 MiB 窗口内乱序写 64 KiB 块，同时穿插读回和 `sync()`；记录合计吞吐、单次调用的最长耗时（尤其是第一次写到 VDL 之后时），以及是否出现 `native-session-closed`；条件允许时再测一块机械硬盘或 U 盘 | 默认窗口下单次调用最长不超过 5 秒，合计写入不低于目标下载速率的 4 倍，没有会话中断 | Windows 窗口上限降到 C+1 个分块后重测；仍不通过就回到评审，考虑稀疏文件或预分配等原生改动（超出本变更范围） |

P1/P2 的结果记录到本文件的 Evidence 小节。没有证据之前，不能把合成测试或吞吐推算当作已验证。

### 2. 方案选择：有界窗口对齐分块（方案 B）

| 维度 | A：固定 N 大段，下载完成后再整文件顺序校验 GCID | **B：有界窗口对齐分块 + 连续前缀折叠（推荐）** | C：全局分块池 + 全量位图 + GCID 分块 SHA-1 乱序聚合 |
| --- | --- | --- | --- |
| 切分方式 | 文件按连接数切成 N 段，每个连接从段首顺序下载 | 固定 8 MiB 网格；连接只能领取连续前缀之后 W 个分块内的空闲分块，序号小的优先 | 固定 8 MiB 网格，任意空闲分块都可以领取 |
| 断点续传 | 每段一个“段起点 + 已写字节 + 段前缀 SHA-256”，状态小；旧检查点只能映射成第 0 段 | 连续前缀加最多 16 个区间，状态有上界；旧检查点直接作为连续前缀使用 | 每个分块一条记录（100 GiB 约 12800 条），需要新表；恢复时要读回所有已完成分块 |
| 校验正确性 | 下载期间没有全文件哈希，GCID 只能在完成后读回计算；落盘损坏要到最后才发现，只能按段定位或整文件重下 | 每个分块的网络流 SHA-256 都在并入前缀时与读回结果比对，落盘错误能及时发现并只重下该块；顺序 GCID 算法不变 | 利用 GCID 两层结构，按块计算 SHA-1 列表后按顺序聚合（8 MiB 是所有 GCID 块大小的整数倍，边界天然对齐），不需要读回；但 SHA-256 仍要完成后顺序读回，而且需要新的乱序聚合实现和参考向量 |
| Windows 文件桥并发写 | 最后一段从约 (N−1)/N 处开始写，第一次写入会触发一次巨大的 NTFS 补零（10 GiB 文件约 7.5 GiB），很可能超过单次调用 15 秒的限制 | 写入最远只比连续前缀多出 W 个分块（默认 64 MiB，上限 128 MiB）；分块按序领取时通常只多出约一个分块；桥接调用天然串行，无需改动 | 写入位置没有上界，补零风险与 A 相同；要么限制窗口（就退化成 B），要么改桥接改用稀疏文件 |
| CDN 限流（429/403） | 并发减半后，会有段没有连接，必须重新划分段；慢段只能拖尾 | 以分块为粒度，天然支持并发增减；被限流的分块放回队列，从已验证位置续传 | 与 B 相同 |
| 地址过期刷新 | 可以使用共享租约 | 共享租约 + 单飞刷新 | 与 B 相同 |
| 复杂度 / 改动面 | 中：段调度简单，但要处理负载均衡和补零 | 中：调度器、租约、区间检查点、折叠读回；`ContentHasher` 不变 | 高：新表、位图、乱序 GCID 聚合，并且仍需窗口才能规避补零 |

选择 B，原因如下：一是旧检查点和 GCID 算法都不用改；二是写入位置有上界，不需要改桥接代码就能规避 NTFS 补零；三是检查点和内存都有上界，与文件大小无关；四是天然支持按分块调整并发。B 的代价是并入前缀时要从磁盘读回一次。这次读回与网络下载在时间上重叠，速率不超过下载速率（最多约 2 MiB/s），远低于桥接的 21 MiB/s；而且下载完成后的读回次数和现在一样，不增加墙钟时间。C 的“GCID 分块 SHA-1 乱序聚合”可以留作以后的优化：B 的 8 MiB 网格已经与 GCID 块对齐，将来切换不需要改检查点网格。

### 3. 分块、窗口与并发数

- **分块大小 S = 8 MiB（8388608 字节）**，与现有每段请求大小相同。网格固定为 `[i·S, (i+1)·S)`，最后一块截到文件末尾。GCID 块大小只可能是 256 KiB、512 KiB、1 MiB、2 MiB，都能整除 8 MiB，所以网格边界一定落在 GCID 块边界上。
- **连接数 C**：配置键 `download_connections`，默认 **4**，允许 **1–8**，**上限 8**。配置时超出范围直接拒绝，不截断。实际使用 `min(C, 尚未完成的分块数)`。
  - 默认 4：在单连接 245 KiB/s 时预计约 1 MiB/s，在吞吐和对 CDN 的压力之间取折中。
  - 上限 8：8 × 245 KiB/s ≈ 2 MiB/s，桥接仍有 10 倍余量，所以上限不是由本地能力决定的。再往上加，主要增加被判为滥用（429/403）的风险，同时扩大窗口、内存和检查点规模，收益也需要 P1 证明。P1 只能在 1–8 内调整默认值，不能突破上限。
- **窗口 W = 2 × C 个分块**：默认 8 个（64 MiB），上限 16 个（128 MiB）。设 `base = ⌊L / S⌋`（L 为连续已验证前缀的长度），连接只领取序号在 `[base, base + W)` 之内、尚未完成也不在途的分块，从小到大领取。W 比 C 多出的部分作为余量，一个慢分块不会立刻挡住其他连接。
- **启动探测**：先只用一个连接请求连续前缀所在的区间。响应头通过 206 和精确 `Content-Range` 校验之后，再每秒最多新增 1 个连接，直到当前并发上限。这样可以避免一开始就同时打出多个请求。
- **使用顺序路径**的条件：文件大小不超过 S（包括零字节）、C = 1，或该文件已持久化为顺序模式（决策 8）。顺序路径就是现有代码，只多一处改动：第一次保存检查点时清空 `ranges_json`。
- 配置入口：`config --connections <1-8>`，`status` 中显示当前值。新值从下一个文件开始生效。`Store` 的 `ConfigKey` 联合类型（现为 `active_account`、`output_root`、`queue_paused`、`clipboard_watch`）增加 `download_connections`。全屏界面的设置页提供同一个选项（←→ 在 1–8 之间调整），经运行时会话命令 `setDownloadConnections` 写入同一个键，与命令行共用校验；设置页显示的是配置值，正在下载的文件不受影响。

### 4. 检查点格式与持久化顺序

`deliveries.checkpoint` 和 `prefix_sha256` 的含义不变：连续已验证前缀 `[0, L)` 的长度及其 SHA-256。结构版本 4 新增一列可为空的 `ranges_json TEXT`：

```json
{
  "v": 1,
  "mode": "parallel",
  "chunk": "8388608",
  "ranges": [
    { "offset": "41943040", "bytes": "8388608", "sha256": "<64 位小写十六进制>" },
    { "offset": "50331648", "bytes": "2097152", "sha256": "<64 位小写十六进制>" }
  ]
}
```

- `mode` 取 `"parallel"` 或 `"sequential"`。`"sequential"` 表示该文件因 Range 异常已回退，后续自动重试不再尝试并行；此时 `ranges` 必须为空。
- `chunk` 是写入时使用的分块大小，用十进制字符串表示。与当前程序不一致时，丢弃全部 `ranges`，但保留前缀。
- 每个区间的不变式：
  - `offset ≥ L`，并且 `offset = L` 或 `offset` 是 S 的整数倍。区间终点 `end = min((⌊offset/S⌋ + 1)·S, size)`；只有从旧的非对齐检查点恢复时，第一个区间才会比 S 短。
  - `0 < bytes ≤ end − offset`。`bytes = end − offset` 表示该分块已完成；否则是部分完成，可以从 `offset + bytes` 继续。
  - `sha256` 是 `[offset, offset + bytes)` 按接收顺序计算的 SHA-256。每个区间用独立的哈希实例，做法与现有 `prefixDigest()` 相同，用 `copy()` 取当前前缀的摘要。
  - 区间按 `offset` 升序排列、互不重叠、最多 16 项，并且全部位于 `[L, (⌊L/S⌋ + 16)·S)` 之内。
- 偏移和字节数都用十进制字符串，延续 bigint 约定。字段缺失、格式错误或违反不变式时，整个 `ranges_json` 视为空，但不连带作废前缀。只有前缀 SHA-256 对不上时才从头开始，这与现在一致。

每次保存按以下顺序执行，同一时刻最多只有一次保存，后来的保存请求会合并：

1. 对每个区间取快照 `(offset, bytes, sha256 副本)`。快照只包含 `write` 调用已经返回的数据，之后的写入不算在内。
2. 对临时文件执行 `sync()`。
3. 从 L 开始，把已完成的区间依次并入前缀（决策 5），可能一次合并多个。
4. 在一个 SQLite 事务里同时写入 `checkpoint`、`prefix_sha256` 和 `ranges_json`。Store 层先校验不变式，不通过就拒绝写入。

触发保存的时机：自上次保存后合计新写入达到 4 MiB、任一分块完成、出错或被中断。现在是每 1 MiB 保存一次，这里放大到 4 MiB，是为了让默认 4 个连接（约 1 MiB/s）下的 `sync` 频率与现在单连接（245 KiB/s，每 1 MiB 一次）大致相同。进程崩溃时，最多丢失最后一次 `sync` 之后的写入，这些字节没有被任何检查点声明，所以不会被误用。

恢复时的核对（下载开始时执行）：

1. 前缀：沿用 `prefix()` 重新读取 `[0, L)` 计算 SHA-256，并与 `prefix_sha256` 比对。不一致时截断到 0、清空区间、从头开始，与现在相同。
2. 区间：对每个满足不变式的区间，要求文件长度不小于 `offset + bytes`，读回 `[offset, offset + bytes)` 计算 SHA-256 并比对。不一致时只丢弃这个区间，磁盘上的旧字节以后会被覆盖；其余区间照常保留。
3. 只有文件长度超过 `size` 时才截断到 `size`；不再截断 L 之后的数据，否则会删掉已验证的区间。
4. 把清理后的结果写回数据库。这一步只会减少声明的数据，因此不需要先 `sync()`。

### 5. 并入前缀与流式 GCID

- 每个连接在接收时，只对自己负责的区间计算 SHA-256（区间内部按顺序接收）。
- 协调器持有一个顺序 `ContentHasher`，状态对应连续前缀 L。恢复时，现有的 `prefix()` 重新读取 `[0, L)` 来重建这个状态。
- 并入：如果从 L 开始的区间已完成，并且已经 `sync()`，就把 `[L, end)`（最多 8 MiB）读进内存，计算 SHA-256 并与该区间记录的摘要比较。
  - 相同：把这段数据送入顺序哈希器，令 `L = end`，删除该区间，然后检查下一个区间。
  - 不同：说明数据在落盘时出了问题。丢弃该区间，下次重新下载；这段数据不能送入哈希器。先读进缓冲区，就是为了让哈希器不需要回滚。
- 当 `L = size` 时调用 `digest()`，得到 GCID 与 SHA-256。如果 GCID 与 `file.gcid` 不同，按现有的 `integrity_mismatch` 处理，从头开始，同时清空 `ranges`，`mode` 不变。如果相同，继续执行现有流程：最后一次 `check()`，转入 `verifying`，`hashFile` 读回，比对 GCID 和 SHA-256，然后 `publishVerified`。
- 结论：GCID 仍然按原算法顺序计算一次，只是输入从网络流换成了“逐块核对过的磁盘数据”。每个分块都会多做一次网络流与磁盘内容的比对，比现在更早发现落盘错误。完成后的校验、发布和回收资格完全不变。顺序路径仍然直接用网络流计算哈希，与现在相同。

### 6. 共享地址租约与版本核对

- 租约包含 `{ generation, endpoint, verifiedAt }`，通过现有的 `check()` 取得：先取元数据，比对副本 ID、大小和 GCID，再用 `originalLink` 和 `secureDownloadUrl` 得到地址。所有连接共用这一份租约。签名地址只存在于内存中，不写数据库或日志；也继续不跟随重定向、不向 CDN 发送账号令牌。
- 新请求开始前，如果租约已超过 **30 秒**，就单飞刷新：只发一次元数据请求，其他连接等待同一个结果。这样版本核对的间隔从“每 8 MiB”变成“最多 30 秒”；现在单连接每 8 MiB 约 33 秒，所以元数据请求频率基本不变，也不随连接数增加。
- 任何一次刷新发现版本变化，都立即中止全部连接，保存检查点，抛出 `version_changed`，由 engine 沿用现有处理：记录错误并重新扫描。
- 收到 401/403 时：如果当前租约仍是这个请求使用的那一代，就单飞刷新到下一代；如果已被其他连接刷新过，就直接用新租约重试。该分块放回队列，已验证的字节保留。
- 如果新一代租约的请求仍然收到 403，而当前并发大于 1，就把并发减半（视为服务端可能在限制并发连接数），2 秒后重试。
- 刷新预算：自上次任何 206 成功以来，因 401/403 触发的刷新累计超过 2 次，就停止全部连接、保存检查点，抛出 `url_refresh_exhausted`。阈值与现在的 `addressRetries > 2` 相同。
- 所有分块完成后，再执行一次 `check()`，与现在相同。

### 7. 限流自适应

- 文件内维护目标并发 `C_target`（配置值）、当前并发 `C_current` 和冷却截止时间。
- **429**：被限流的分块放回队列，保留已验证字节；`C_current = max(1, ⌊C_current / 2⌋)`；冷却时间为 `Retry-After`，限制在 1–60 秒，没有该头时取 5 秒。冷却期间不发起新请求；在途连接继续传输，在途数量降到新上限以下之前，也不补新连接。
- 上报条件：收到 429 时 `C_current` 已经是 1，或 `Retry-After` 超过 60 秒。这时停止全部连接、保存检查点，抛出带 `retryAfterMs` 的 `rate_limited`，由 engine 走现有的账号限流和 `transientFailure` 路径，不触发云端回收。
- 恢复：连续完成 16 个分块（约 128 MiB）且期间没有因限流降并发，就把 `C_current` 加 1，直到 `C_target`。
- 跨文件记忆：engine 在内存中按账号记住最后的 `C_current`，下一个文件从这个值开始。不持久化，重启 `watch` 后回到配置值。
- **402 / 流量配额不足**：立即停止全部连接，保存检查点，抛出 `traffic_quota`，由 engine 进入现有的流量暂停，不在文件内重试。
- 5xx 按单个请求的网络失败处理（决策 8）。
- 实现说明：同一波限流常同时打到多个在途连接。冷却期内再收到 429 只把分块放回队列，不再次减半，避免一波限流把并发直接降到 1 并上报。

### 8. 失败预算与回退策略

| 情况 | 处理 |
| --- | --- |
| 单个请求网络错误、响应头 20 秒超时、响应体 60 秒停滞、内容被截断、5xx | 分块放回队列，保留已验证字节，从 `offset + bytes` 继续，换连接或新建连接都可以。超时值与现在相同 |
| 文件内预算耗尽 | 同一分块连续失败 3 次，或全文件连续 6 次请求失败且期间没有分块完成：停止全部连接，保存检查点，抛出最后一次的错误码（`network_failure` / `truncated_content`），由 engine 计入文件级有限重试。任一分块完成后计数清零 |
| 第一次探测时 L = 0、没有区间，却收到 200 整份内容 | 服务端不支持 Range。改用顺序方式接收这个响应（同现有 `fullResponse`），并持久化 `mode = "sequential"` |
| 已有进度时收到 200、`Content-Range` 不匹配、经过内容编码，或响应体超出请求范围 | 不写入该响应，停止全部连接。如果该文件是第一次出现这种情况，就持久化 `mode = "sequential"`，清空区间，截断到 0，用顺序方式重新开始（对应现在的 `rangeRestarts ≤ 1`）；再次出现则抛出 `range_mismatch` |
| 本地写入错误（ENOSPC、EACCES、`native-session-closed` 等） | 停止全部连接，等待在途写入结束，再尽力保存。如果 `sync` 也失败就不写新检查点，沿用上次已提交的检查点（它只声明早先已同步的数据）。抛出原错误，engine 的暂停规则不变 |
| 用户中断（Ctrl+C，或 TUI 的取消、暂停） | 停止全部连接，在有限时间内等待在途写入结束，保存检查点后抛出，与现在相同 |
| 完成时 GCID 不符 | 按现有逻辑从头开始，同时清空区间。`mode` 不变，因为这不是 Range 异常 |
| 显式 `retry` | 清除 `mode = "sequential"`，允许重新尝试并行（服务端行为可能已经变化）。自动重试保留该标记 |

实现说明：探测收到 200 时，协调器不复用这个响应，而是取消它、持久化顺序模式后交给顺序路径从偏移 0 重新请求；顺序路径在偏移 0 本来就接受 200 整份内容，只多一次请求头往返，换来两条路径之间没有共享的响应流。回退后顺序路径不再给 Range 异常额外的重启机会，再次出现即报 `range_mismatch`。协调器等待冷却与慢启动时以不超过 100 ms 的间隔轮询，不按注入时钟的差值直接睡眠。

### 9. Windows 文件桥与本地空间

- 每个文件只打开一个 `LocalFile` 句柄，所有连接共用，不额外打开句柄。
- 不修改桥接代码：`ProcessBridge` 已经把所有调用排成 FIFO，每个 64 KiB 写入都自带偏移，不存在位置竞争。默认 4 个连接时，写入和并入读回合计约 2 MiB/s，即使上限 8 也只占桥接能力的约 20%（读速度假设与写速度相当，由 P2 验证）。
- `sync()` 执行期间会占住队列，写入随之排队，网络读取会受到背压。现有的 60 秒停滞计时只包住 `reader.read()`，不包住写入，所以慢的 `sync` 不会被误判为网络停滞，这一点保持不变。
- NTFS 补零（待验证）：分块按序号从小到大领取，正常情况下新分块紧挨着写入前沿，每次补零最多约一个分块；只有带着零散区间恢复时，才可能补零接近整个窗口（默认 64 MiB，上限 128 MiB）。每段空间只会补零一次。如果 P2 测出补零超过限制，就把 Windows 的窗口降到 C+1。
- 本地容量预检：剩余量仍保守地按 `size − L + 1 MiB` 计算，不把窗口内已写的区间算作已占用（NTFS 上空缺本来就会被补零占用）。最多多估 128 MiB，符合现有“剩余数据及临时开销”的要求。`remainingBytes()` 只核对前缀；前缀无效时重置全部，有效时不截断 L 之后的数据。文件长度超过 `size` 时才截断到 `size`。
- 恢复时的读回量为 L 加上各区间的字节数，与现在读回 L 是同一量级。

### 10. 与 `add-interactive-tui` 的边界

`add-interactive-tui` 的执行器中断与进度事件改动已在 main（截至 `3111468`），本变更直接在其上实现：

- `download()` 的进度回调仍是 `(bytes: bigint) => void`，值为 `L + Σ 区间已接收字节`，已经包含尚未保存的字节。`Engine.step` 每 250 ms 至多转发一次，事件为 `{ type: "progress", id, bytes, size }`，结构不变。丢弃区间或 GCID 不符重置时，这个值可能减小；TUI 的 `SpeedMeter`（`src/tui/speed.ts`）在数值减小时清空该文件的速度窗口，已有测试覆盖。
- TUI 主面板与详情页的断点字节来自 `Store.fileViews()` 中对 `deliveries.checkpoint` 的子查询。改为区间检查点后，这里应返回已持久化的字节数（`L + Σ 已保存区间字节`），由任务 2.2 的辅助查询提供。
- 用户中断：`RuntimeSession`（`src/runtime/session.ts`）为每一步创建独立的中断控制器，取消当前文件或暂停队列时中断该步骤，并等待它返回后再写任务库。`download()` 收到的 `signal` 与 Ctrl+C 走同一条路径，因此决策 8 的“用户中断”处理同时覆盖 TUI 的取消和暂停。
- 本变更只改 `engine.ts` 中调用 `download()` 的参数，以及跨文件并发记忆。

### 判定与 1.3 建议

- P1 通过决策 1 的标准：4 个连接的合计吞吐是单连接的 5.88 倍（标准为不低于 2.5 倍），正常运行中没有 429/403。本变更继续，进入第 2 组的前提成立。
- 建议默认连接数保持 4：P1 中 4 连接已有 5.88 倍收益且没有限流；P2 中 4 连接在 SSD 与机械硬盘上都有 7 倍以上余量。
- 用户已于 2026-10-15 评审确认默认 4、上限 8、Windows 窗口 2C。
- 建议上限保持 8，Windows 窗口保持 2C：8 连接在 P1 中收益更高（8.26 倍）、同样没有限流，在 SSD 上通过 P2；在机械硬盘上只有目标的 3.3–3.7 倍，略低于 4 倍，而把窗口降到 C+1 不能改善。按本次实测的实际下载速率（8 连接约 0.35 MiB/s），机械硬盘上的桥接仍有约 18 倍余量；即使按单连接 245 KiB/s 估算（8 连接约 1.9 MiB/s）也有 3.3 倍。因此 8 连接作为用户显式配置的选项保留，不为机械硬盘单独限制，也不在本变更中改动原生桥接。

| `Content-Range` 错误 | `tests/range-worker.test.ts`；协调器“已有进度时出现 Range 异常”；真实文件桥“已有进度时 Range 异常” | 第一次清空区间、截断到 0、改走顺序路径；再次出现报 `range_mismatch` |

| 停滞 | `tests/range-worker.test.ts`“停滞”；协调器“连接停滞超过时限后换连接继续” | 视为网络失败，换连接继续 |
| 402 流量 | 协调器“流量配额不足”；真实文件桥“流量额度只读验证后才恢复” | 立即停止，检查点可核对，engine 进入流量暂停 |
| 本地磁盘写满、会话中断 | 协调器“多个连接写入时本地写入失败”（ENOSPC、`native-session-closed`） | 停止全部连接，原错误上报，engine 暂停分类不变 |
| 进程崩溃后恢复 | 协调器“在 sync 前、sync 后事务前、事务后崩溃”“中断” | 检查点从不声明未落盘的字节，重启后核对并完成 |
| 临时文件被改动 | 协调器“前缀被改动”“只有被改动的区间重下”“文件被截短/末尾有多余数据”“读回摘要与接收时不符”；真实文件桥“同大小但内容被篡改” | 只丢弃对不上的部分；GCID 不符时从头开始并清空区间 |

规格增量中的其余场景：小文件或单连接配置由现有 `tests/transfer.test.ts`、`tests/engine.test.ts` 与“单连接配置走顺序路径”覆盖；连接数配置与设置页由 `tests/connections.test.ts`、`tests/lifecycle.test.ts`、`tests/tui-screens.test.tsx` 覆盖；跨 128 MiB GCID 分块阈值由协调器“跨 128 MiB GCID 分块阈值”覆盖。

## Risks / Trade-offs

- [CDN 按账号或 IP 总量限速，并发没有收益] → P1 先测，收益不足就停止本变更，默认行为不变。
- [并发触发 CDN 风控或账号风险] → 默认 4、上限 8、慢启动、429/403 时并发减半，并且不同时下载多个文件。
- [多个连接共用签名地址被拒绝] → P1 验证；如果不允许共用，就回到评审，改为每个连接各自取地址，同时限制元数据请求频率。
- [队头分块过慢，窗口被卡住] → 窗口留出 C 个余量，60 秒停滞超时后该分块会换连接。本变更不拆分队头分块；文件末尾分块数少于连接数时，多余的连接会空闲，可以作为后续优化。
- [NTFS 补零超过桥接单次调用的 15 秒] → 写入位置有上界、P2 实测、必要时降低 Windows 窗口；仍不通过就回到评审，不在本变更里修改原生桥接。
- [并入读回带来额外 I/O] → 与网络下载在时间上重叠，速率不超过下载速率；完成后的读回次数不变。
- [`ranges_json` 损坏或被篡改] → 先校验不变式，再用 SHA-256 读回核对；失败时只丢弃区间，不会信任未核对的数据。
- [回退到顺序模式后一直不并行] → 只有 Range 异常才会持久化顺序模式，显式 `retry` 会清除它。
- [进度数值可能回退] → 在设计和 TUI 边界中写明；不影响完成判定。

## Migration Plan

1. 先完成 P1、P2 并记录证据。P1 不通过就停止。
2. 任务库结构从 3 升到 4，沿用现有迁移事务和升级前备份：`ALTER TABLE deliveries ADD COLUMN ranges_json TEXT;`。已有检查点（`checkpoint` 与 `prefix_sha256`）继续作为连续前缀，`ranges_json` 为 NULL，正在下载的文件不需要重下。
3. `download_connections` 未设置时取默认值 4。如需临时退回现有行为，用户执行 `config --connections 1`，下一个文件起改用顺序路径；第一次保存时会清空 `ranges_json`，窗口内未并入前缀的分块会被丢弃并重新下载（最多 128 MiB）。
4. 降级到旧程序时，沿用“旧程序拒绝写入更高结构版本”的规则。如需回退，只能继续使用新版本，或者按现有规则恢复备份，并先核对外部状态。
