# Design

## Context

动机见 [proposal.md](proposal.md)。基线为 `main` 截至 `cddae01`：`RuntimeSession`（`src/runtime/session.ts`）循环调用 `Engine.step`，命令放进队列，在两次步骤之间按序执行；暂停队列和针对当前串行项的取消会先中断当前步骤。`Engine` 有下载池（`add-concurrent-file-downloads`），`stopActive(match)` 可以中断匹配的池中文件并等它们保存检查点。自动回收由 `SpaceManager.ensure` 在转存前按需执行，只删除已交付、有归属证据的副本。任务库结构版本为 4。

## Goals / Non-Goals

**Goals:**

- 设置修改、粘贴分享、取消或暂停非当前项等命令在任务运行中立即生效。
- 文件与分享可以单独暂停和继续，持久化；另有全部暂停与全部开始。
- 用户可以立即释放所选任务在 PikPak 中的云端副本，失败时不影响账号状态。

**Non-Goals:**

- 删除任务记录或本地文件、批量多选、回收站操作。
- 改变自动回收的触发条件和资格。

## Decisions

### 1. 命令执行：立即执行，只有中断类命令先停下目标

- 会话把命令分成两类。中断类：`pauseQueue`；以及目标正是当前串行步骤所处理的文件或分享的 `cancel`、`pauseTask`。其余命令（设置、粘贴、恢复、重试、全部开始、手动释放，以及目标不在串行步骤中的取消和单项暂停）都是立即类。
- 立即类命令进入一条串行的 Promise 链，按提交顺序立即执行，不等当前步骤。它们要么只写配置或任务库中与当前步骤无关的部分，要么先用 `engine.stopActive` 停下下载池中的目标文件。
- 中断类命令沿用现有机制：放进队列并中断当前步骤，步骤在安全点返回后，主循环在开始下一个步骤之前处理队列。这样“写入暂停”和“开始下一个步骤”之间不会交错。
- 备选：所有命令都立即执行，再用“暂停中”计数阻止主循环开始新步骤。被否决：需要额外的握手，而只有中断类命令真正需要等当前步骤停下。
- 修改下载目录与“迁移尚未开始的分享”现在可能与串行步骤并发。`FileWorkspace.open` 读取分享目录、打开根目录，再写入根目录身份；若在打开期间分享被迁移到新目录，就关闭刚打开的根目录，按新目录重新打开。写入根目录身份与迁移都在同步的数据库语句里完成，两者不会交错，因此不会出现“目录是新的、身份却是旧目录”的记录。

### 2. 单项暂停的数据与调度

- 任务库结构升到 5：`files.paused`、`shares.paused`（0/1，默认 0），沿用升级前备份。
- 暂停文件只标记该文件；暂停分享标记分享（不逐个标记文件）。继续分享时同时清除该分享和它所有文件的暂停标记；继续文件只清除文件标记，若其分享仍暂停，界面显示分享暂停。已完成的文件忽略暂停。
- `nextFile` 跳过已暂停的文件和属于已暂停分享的文件；`nextScan` 跳过已暂停的分享。暂停与取消相互独立：取消表示不再执行、需要 `r` 恢复；暂停表示稍后继续、用同一个键继续。
- 暂停正在执行的目标：池中的文件用 `engine.stopActive` 停下；串行步骤中的目标由中断类命令先中断步骤。停下后写标记，检查点由下载路径自己保存。
- 界面显示：文件或其分享被暂停时，文件行显示“⏸ 已暂停”；分享行在计数后显示“· 已暂停”；暂停的文件计入分享的“暂停”计数。

### 3. 全部暂停与全部开始

- 全部暂停就是现有的队列暂停 `queue_paused`。全部开始清除队列暂停，并清除全部单项暂停标记（分享与文件），不改变取消标记。
- 按键 `P`：只要队列暂停或存在任何单项暂停，它就执行“全部开始”；否则执行“全部暂停”。按键提示随状态显示“P 全部开始”或“P 全部暂停”，用户始终看得到按下会发生什么。
- 按键 `p`：对选中的文件或分享执行暂停或继续，提示显示“p 暂停”或“p 继续”（在 100 列内放下全部按键提示）。
- 备选：`P` 只按队列状态切换。被否决：只有单项暂停时，用户得先全部暂停再全部开始，才能一次恢复所有暂停项。

### 4. 手动释放云端副本

- 资格：副本由本工具创建（`ownership='created'` 且有归属证据），状态为保留中；引用它的文件都不在下载池中、也不是当前串行步骤的目标。文件可以已完成，也可以未完成（排队、暂停、取消、失败、等待）。分享上执行时，对其中每个有合格副本的文件分别处理。
- 流程（在云端操作锁内）：用元数据确认副本仍是本工具创建时的那份（`unchangedOwnedCopy`）；写删除意图；以静默模式调用 `files:batchDelete`，发送前把副本标为删除中；之后沿用 `SpaceManager.reconcile` 核对删除结果与容量变化。
- 服务端明确拒绝（401 以外的 4xx，例如没有永久删除权限）：删除没有发生，副本恢复为保留中，删除意图记为已确认、结果为被拒绝，界面提示原因。静默模式不暂停账号、不记录账号限流，因此权限不足只影响这一次操作。其他未知结果沿用现有规则，标记为需要核对。
- 未完成的文件：副本删除后，若文件处于下载中、等待转存完成或转存中，就改回“就绪”（不消耗重试次数），断点保留；下次执行时 `copyForFile` 找不到保留中的副本，按现有流程从分享重新转存，再从断点继续。分享已失效时，重新转存会按现有规则报告需要提取码或分享不可用。
- 云端操作锁：`Engine` 内一把异步互斥锁，自动回收（`SpaceManager.ensure`）、启动时对删除意图的核对与手动释放都在锁内执行，避免两者同时为同一份副本发出删除。
- 执行方式：`releaseCopy` 命令只做同步的资格检查，把涉及的文件加入“释放中”集合（调度跳过它们）后立即返回；删除与核对在锁内于后台进行，结果以事件报告。这样等待删除核对（最多约 60 秒）时不会阻塞其他命令。会话停止时随运行信号中断，已发出的删除留给下次启动核对。
- 引擎记录当前串行步骤所选的文件；它、下载池中的文件和正在释放的文件都不能被释放。资格检查与选择文件都是同步的，两者不会交错。
- 已完成文件的副本被手动释放后，自动回收的候选列表自然不再包含它（状态已不是保留中）。

### 5. 界面

- 主面板按键：`p` 暂停或继续此项、`P` 全部暂停或全部开始、`x` 释放云端副本；`c` 取消、`r` 重试保持不变。
- `x` 打开确认框：说明将永久删除 PikPak 中的这份云端副本、本地文件保留；未完成的文件额外说明“继续时会从分享重新转存，分享失效时将无法完成”。没有合格副本时不打开确认框，只在事件区说明原因（没有云端副本、正在下载、不是本工具创建）。
- 事件区报告释放结果：已释放的副本数与空间，或被拒绝的原因。释放后刷新云盘容量。

### 6. 任务在本地还是云端

用户在 2026-10-15 实测手动释放后反馈：释放成功了，列表却看不出变化，因为主面板从不显示云端副本的状态。用户要求看到每个任务在本地、云端还是两处都有。

- 文件行在状态文字后面加一个淡蓝色（`blueBright`）的单宽符号 ☁（U+2601，不带 emoji 变体选择符），表示云盘中仍有最近一份副本（保留中、删除中或受保护），也就是还占着云端空间、可以按 x 释放。
- 已完成的文件默认就在本地，不另加标记；交付的本地文件已不在（被移动或删除）时，状态写“已完成 · 本地文件已不在”（警告色）。四种组合都能分辨：“已完成 ☁”两处都有，“已完成”只在本地，“已完成 · 本地文件已不在 ☁”只在云端，“已完成 · 本地文件已不在”两处都没有。下载了一部分的文件由进度条表示。
- 分享行只要还有文件在云端，就在计数末尾加一个 ☁，不带数字；本地缺失时计数中追加“· N 本地缺失”。已完成的分享默认折叠，释放后不展开也能看到变化。
- 演变过程：第一版在大小与状态之间放了一列“本地 / 云端”文字，用户觉得太乱；第二版改成行尾的 💻 ☁️ emoji，在用户的 Windows Terminal 字体下渲染得很小，还吞掉了后面的空格，分享行“☁️ N”和重复的目录也很杂乱。用户从三种方案里选了现在的淡色单宽符号。
- 详情页增加“本地文件”一行（存在、已不存在、已下载部分、尚未下载）。“云端副本”一行的文字改为：保留中（可按 x 释放）、删除中、已删除（不在云盘中）、受保护。
- 本地是否存在只对已完成的文件检查：取交付记录中的目标路径做一次 `stat`。不存在（ENOENT、ENOTDIR）记为缺失；其他错误保留上次结果；还没检查过的按存在处理。检查只读，不打开文件，也不改动任务库。它随本地剩余空间每 10 秒刷新一次，文件完成时也立即刷新。
- 名称列为云端标记让出 2 列：`nameWidth = clamp(columns - 74, 18, 48)`，100 列窗口下为 26 列。

### 7. 释放后删除已完成任务的记录

用户同日反馈：释放过的任务仍留在列表里。可选方案有三种：从列表隐藏、保留并标出位置、删除任务记录。用户选择删除任务记录。

- 已完成文件的副本释放成功（核对为已删除，或核对时副本已不在云盘中）后，删除该文件的任务记录。删除的范围是：文件行、交付记录、操作记录、它转存产生的副本记录与引用、名称预留、扫描关联。本地文件不动。
- 同一个 `x` 也能删除已完成、云盘中已没有副本的文件记录（例如副本早先已被自动回收），这时确认框标题为“删除任务记录”。
- 只有满足以下全部条件的文件记录才会删除：已完成；引用的副本都已删除；它转存产生的副本没有被其他文件引用；没有未核对的操作；没有账号暂停指向它。不满足的保留并照常显示。
- 分享的文件记录都删除、扫描已完整完成、且没有待执行的重新扫描时，分享记录（扫描、目录、名称预留）一并删除；不再被引用的提取码由 `collectShareAccess` 回收。
- 事件先报告、再删除：事件区按 ID 查名称，删除后就查不到了。资格检查与删除都是同步的，中间没有 await。
- 未完成文件的副本释放后，记录保留，文件改回排队，与决策 4 相同。
- 之后再复制同一分享，它会作为新任务重新扫描和下载。分享还有其他文件、因此记录没被删除时，重新扫描（复制同一分享、对分享按 r、或版本变化触发）会让已删除记录的文件作为新任务重新出现。这是有意的取舍：用户的选择是“删除记录”，而不是保留墓碑记录。

### 8. 按本地下载目录分组

用户同日反馈：每个分享行右侧都显示同一个本地目录，太重复，应当按本地路径分组。

- 列表按分享的下载目录分组：每组先有一行“下载到 <目录>  · N 个分享”，下面是该目录下的分享与文件。目录按首次出现的顺序排列，组内分享保持原顺序。分享行不再显示目录。
- 分组行只用于显示，不可选中：上下移动与翻页跳过它；到达列表一端时停在最近的分享上。选中某组第一个分享并滚到顶部时，滚动位置上移一行，让该组的目录行一起显示。
- 所有任务都在同一目录时也显示这一行，用户随时知道文件下载到哪里。

## Risks / Trade-offs

- [现有授权没有永久删除权限] → 手动释放只提示“没有永久删除权限”，不暂停账号；用户执行这一操作同时完成删除权限的实测。自动回收在同样情况下仍按现有规则暂停“权限”，这是已有行为，不在本变更内改变。
- [未完成文件的副本被释放后分享失效] → 确认框明确说明；文件保留断点与记录，用户可以之后提供新的分享资料。
- [立即执行的命令与串行步骤并发] → 只有中断类命令会影响当前步骤，且仍走“先中断再写”的路径；目录迁移与工作区打开之间的竞态由第 1 节的重开处理。
- [单项暂停与取消概念相近] → 两者在界面中使用不同图标与文字，取消仍需确认。
- [删除记录后重新扫描会让文件再次出现] → 只在分享还有其他文件时发生；确认框和文档说明了重新复制分享会重新下载。

## Migration Plan

任务库结构从 4 升到 5，沿用升级前备份与“旧程序拒绝写入更高版本”的规则；新增两列默认 0，已有任务不受影响。

## Open Questions

- 已解决（2026-10-15 用户实测）：现有 OAuth 授权（`files:manage cloud_download share account`）允许 `files:batchDelete`。对一个已完成文件执行手动释放后，删除意图核对为 `deleted`：请求被接受，副本随后不可见（404），云盘用量按副本大小减少。授权页没有“永久删除”勾选项，但这不代表删除不可用。
