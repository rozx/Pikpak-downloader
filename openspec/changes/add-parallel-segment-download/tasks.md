# Tasks

本变更必须等 P1、P2 验证（第 1 组）通过后才能进入实现。实现依赖 `add-clipboard-download-workflow` 的现有代码；`add-interactive-tui` 的执行器中断（`RuntimeSession` 每步独立中断控制器）与进度事件 `{ type, id, bytes, size }` 已在 main（截至 `3111468`），涉及 `src/runtime/engine.ts` 的任务直接在其上实现。各组区分真实接口、模拟服务和实际操作系统三类验证，不用其中一种代替另一种。

## 1. Feasibility

- [x] 1.1 P1 真实 CDN 验证：使用明确指定的测试副本（≥ 256 MiB），在同一个签名地址上用 1/2/4/8 个并发 Range 连接各运行 3 次。记录合计吞吐、每个响应的状态码与 `Content-Range`、429/403/402 次数和 `Retry-After`、多个连接能否共用同一地址，以及地址从取得到失效的时长。验收：结果按 design.md 决策 1 的标准判定，记录到 Evidence；不输出签名地址、凭据或文件名。结果（2026-10-15，274.1 MiB 副本）：1/2/4/8 连接中位数 0.042/0.081/0.247/0.347 MiB/s，4 连接为单连接的 5.88 倍，8 连接为 8.26 倍；36 个响应全部是精确的 206，没有 429/403/402；8 个连接共用同一签名地址；地址约 12 小时有效，探测 19 分钟仍可用。
- [x] 1.2 P2 Windows 文件桥验证：用编译后的产物在 NTFS 上运行 4 和 8 个写入者，在 64 MiB 和 128 MiB 窗口内乱序写入，同时穿插读回和 `sync()`。记录合计吞吐、单次调用的最长耗时（尤其是第一次写到 VDL 之后时），以及是否出现 `native-session-closed`；条件允许时再测一块机械硬盘或 U 盘。验收：按决策 1 判定；不通过时记录 Windows 窗口的调整结果，或回到评审。结果（2026-10-15，见 design.md Evidence）：SSD 上 4/8 连接、机械硬盘上 4 连接通过；单次调用最长 2.2 秒，补零 128 MiB 窗口不超过 0.9 秒，无会话中断；机械硬盘上 8 连接只有目标的 3.3–3.7 倍，窗口降到 C+1 后为 3.28 倍，回到 1.3 评审。
- [x] 1.3 汇总 P1、P2，确认或在 1–8 内调整默认连接数，确认 Windows 窗口大小。验收：P1 无增益时停止本变更并记录原因；通过后才开始第 2 组。结果（2026-10-15，用户评审确认）：默认 4 个连接、上限 8，Windows 窗口保持 2C；机械硬盘上 8 连接的余量不足 4 倍，作为显式配置保留，不单独限制。

## 3. Segmented Download Core

- [x] 3.1 分块网格与窗口调度器：8 MiB 分块，窗口 W = 2C，按序号从小到大领取，先探测后每秒最多新增 1 个连接，有效并发为 `min(C, 尚未完成的分块数)`。验收：纯逻辑测试覆盖非对齐的旧前缀、最后一个短分块、窗口边界，以及并发上限变化时不补连接。
- [x] 3.2 共享地址租约：单飞刷新，最长 30 秒有效，每次刷新都核对版本，401/403 按代数刷新，并计算刷新预算。验收：多个连接同时收到 403 时只发一次元数据请求；刷新时版本变化会中止全部连接；预算耗尽时报 `url_refresh_exhausted`；签名地址不进入数据库或日志。
- [x] 3.3 连接工作者：发送 Range 请求，严格校验 206、`Content-Range` 与内容编码，计算区间 SHA-256，从部分完成的区间继续，沿用 20 秒和 60 秒超时。验收：契约测试覆盖正确的 206、响应体超出范围、截断、停滞，以及从区间中间继续。
- [x] 3.4 保存周期：取快照、`sync()`、读回并入前缀、在一个事务里写入；触发条件为新写入 4 MiB、分块完成、出错或中断；同一时刻只有一次保存并合并后来的请求。验收：在 `sync` 前后和事务前后注入崩溃，检查点从不声明未同步的字节；读回摘要不符时丢弃该区间，且不送入顺序哈希器。
- [x] 3.5 恢复核对：分别核对前缀和每个区间，只丢弃不一致的区间；`remainingBytes()` 不截断 L 之后的数据，只在文件超过 `size` 时截断。验收：覆盖前缀被改动（从头开始）、单个区间被改动（只重下该块）、文件被截短，以及在区间之外追加了垃圾数据。
- [x] 3.6 完成校验：L 到达 `size` 后比对 GCID，然后沿用现有的 `verifying` 读回、比对 GCID 与 SHA-256 和 `publishVerified`；GCID 不符时从头开始并清空区间。验收：同大小但内容被篡改的响应不能完成；GCID 参考向量和跨 128 MiB 分块阈值的测试在并行路径下都通过。

## 4. Failure Handling and Fallback

- [x] 4.1 限流自适应：429 时并发减半，按 `Retry-After` 冷却（限制在 1–60 秒，缺省 5 秒）；并发为 1 或等待超过 60 秒时上报 `rate_limited`；连续完成 16 个分块后加 1；402 立即停止并报 `traffic_quota`；新一代租约仍收到 403 时也减半。验收：可控服务测试证明部分连接限流时不消耗文件级重试，而升级上报后 engine 走现有的账号限流和流量暂停路径，不触发回收。
- [x] 4.2 文件内失败预算：同一分块连续失败 3 次，或全文件连续 6 次失败且期间没有分块完成，就上报；本地写入错误和中断时，先停止全部连接，等待在途写入结束，再保存检查点。验收：在多个连接同时写入时注入 ENOSPC、`native-session-closed` 和 Ctrl+C，检查点都可以核对，engine 的暂停分类不变。
- [x] 4.3 回退到顺序模式：没有进度时探测返回 200，就顺序接收该响应；已有进度时遇到 Range 异常，第一次重启为顺序模式，第二次报 `range_mismatch`；持久化 `mode = "sequential"`，显式 `retry` 时清除；顺序路径第一次保存时清空区间。验收：契约测试覆盖这三种情况，C = 1 和小文件时的行为与现有测试一致。
- [x] 4.4 Engine 集成：传入连接数配置，在内存中按账号记住降低后的并发，进度回调报告 `L + Σ 区间字节`。验收：现有 engine 测试全部通过；进度值在正常下载时单调增加，在区间被丢弃或重置时可以减小；与 TUI 的进度事件 `{ type, id, bytes, size }` 兼容。
- [x] 4.5 停止时快速保存：中断或失败时只同步并保存区间，不再把已完成的队头分块读回并入前缀；停止开始后正在进行的并入在下一个分块处结束。来源：用户实测多个文件同时下载时退出很慢（每个文件最多需读回窗口内 64 MiB，Windows 文件桥串行处理）。验收：测试证明停止后没有任何读回，检查点中的区间在下次启动时全部通过核对并完成下载。
